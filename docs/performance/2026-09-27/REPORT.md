# Flutter / Dart 数据处理实测（2026-09-27）

这是重构前的历史基准。当前实现与复测结果见[重构对比报告](refactor/REPORT.md)。下方复测方法对应当时的源码；在当前源码上运行会得到优化后的结果。

测试直接导入本项目的生产函数，在独立 Windows Flutter **Release AOT** 程序中执行。没有修改业务实现。环形数值缓存仅是基准程序中的对照原型。

硬件：12th Gen Intel(R) Core(TM) i5-12450H，8 核 / 12 线程，内存 31.71 GiB。
软件：Flutter 3.47.0，Dart 3.13.0；"Windows 10 Pro for Workstations" 10.0 (Build 26200)。
最终共 2 个独立进程、每轮 39 项测量；各轮均通过显式校验。
另执行 3 个独立进程的心跳专项，每轮 4 项测量。

## 结论

Dart 可以承担本项目的数据处理，但当前缓存实现限制了持续采样吞吐，大 FFT 不适合放在界面线程。多后端兼容仍适合采用统一数据协议：pyOCD / probe-rs 负责硬件，共用 Dart 数据与分析层。

若未来后端能提供 **32 路 × 每路 10 kHz**，每 6.4 ms 就产生一批数据。按当前实测，处理 1 秒的数据约需 **3.32 秒**主线程时间，仅这条链路就无法持续跟上，还未计入绘图和其他界面工作。1 kHz 的对应负载为其十分之一。

对照结果说明这里有很大的实现优化空间；倍率只适用于这项满缓存写入测试，不能解释为整个应用能加速同样倍数。对照使用 Float64List 环形缓存，避免 List<Offset> 头删造成的逐点搬移及 Offset 分配。已校验环形历史的时间和值与生产缓存一致，并检查所有链路的帧数、计数和末值。

## 主 isolate 响应

以 16 ms 定时器模拟事件循环心跳，连续执行三次 262,144 点 FFT。以下是每轮最大心跳间隔的区间，**不是实际界面帧时间**。优先采用独立进程的心跳专项结果，避免前序大 CSV / 百万点 FFT 及其内存回收的干扰；完整矩阵中的心跳观测也保留在原始 JSON 中。

| 场景 | 最大心跳间隔 ms（各轮区间） |
| --- | ---: |
| 空闲基线 | 17.53–17.95 |
| 主 isolate 同步执行 | 214.20–245.14 |
| 每次 Isolate.run，传入点列表并返回完整频谱 | 61.95–64.84 |
| 常驻 worker，预载点列表，仅返回峰值摘要 | 24.02–26.73 |

后台执行改善了响应，但大对象传输、内存分配和 GC 仍可能带来停顿，不能据此保证稳定 60 FPS。常驻 worker 的初始输入装载时间单独记录为 workerStartupMs，未计入该场景的心跳测量；它也没有返回完整频谱，所以与一次性 isolate 场景的传输成本不同。

## 测量方法与边界

- 三次预热，按预热时间选择每块重复次数，目标每块约 20 ms；15 块为主，大任务为 7 或 9 块。
- 中位数及 P95 来自“每块平均每次耗时”；P95 不是逐次延迟 P95。绘图离屏项为预热三次后的九次单独测量。
- 输入生成、初始缓存填充不计时，计时期间的内存分配与 GC 计入。两轮为不同进程，顺序执行，未并发跑其他基准。
- 所有函数结果被消费；校验二进制帧计数、环形历史一致性、FFT 峰值、CSV 行列数和绘图曲线开启状态。
- 没有连接真实探针，没有计入 Python/Rust 数据生产、USB/SWD、进程管道 I/O、文件录制、Widget 构建、多窗口同步或屏幕呈现。
- 单台机器的合成数据测试，后台系统负载、供电和调度未严格控制；不能当作语言排名或全应用的端到端容量认证。
- 各轮整个进程峰值 RSS：1493 MiB, 1544 MiB。这是包含百万点 FFT 和大 CSV 场景的进程峰值，不是日常采样缓存占用。
